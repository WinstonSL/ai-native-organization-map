# 内容更新指南（给 AI Agent）

> 本文件是**给未来负责更新知识的 AI Agent 看的操作手册**。
> 人类用户会把"更新/补全知识"的任务交给某个 Agent，该 Agent 必须严格按本指南执行，
> 以保持整个学习地图的调性、格式与质量统一。
>
> 配套阅读（顺序即优先级）：
> 1. `AGENTS.md` — 项目身份、约束、**内容编辑标准**（第 9 节）。
> 2. 本文件 — 具体操作步骤。
> 3. `docs/CONTENT_GOVERNANCE.md` — 决定"收不收"的判断标准。

## 0. 对执行 Agent 的能力要求

在接受更新任务前，确认你（Agent）具备：
- **能访问外网**：抓取并验证 URL 是否可达（核实链接是硬性要求）。
- **能运行 Node.js（18+）**：用于跑链接体检脚本 `tools/check-links.mjs`。
- **能执行 git**：提交并推送到默认分支 `main`（推送后 GitHub Pages 自动重新发布）。

若不具备以上能力，请明确告知用户你无法独立完成，不要凭记忆编造链接或跳过验证。

## 1. 知识存放在哪里

- **所有知识内容在 `content.js`**（纯数据，不含交互逻辑）。更新知识**只改这个文件**。
- `app.js` 是交互逻辑（渲染、路由、搜索、学习状态）。**不要为了改内容去动 `app.js`。**
- `content.js` 里有四块数据 + 一张日期表：
  - `modules` — 12 个模块。每个模块含：`id / n / p / title / q / desc / concepts / tools / learn`，以及可选的 `deep`（深度章节）。
  - `products` — 产品/工具索引。
  - `conceptDefs` — 概念名 → 一句话释义。
  - `moduleUpdated` — 每个模块的最后更新日期（`{模块id: 'YYYY-MM-DD'}`）。

## 2. 标准更新流程（10 步）

1. **读法规**：先读 `AGENTS.md`（尤其第 9 节内容编辑标准）、本指南、`CONTENT_GOVERNANCE.md`。
2. **判断要不要收**：按 `CONTENT_GOVERNANCE.md` 判断。收持久的架构模式 / 开放协议 / 新产品抽象 / 影响企业部署治理的东西；**不收**模型跑分新闻、无落地的炒作、与已有项近乎重复的产品。
3. **定位**：这条知识属于哪个模块？是新增概念（`conceptDefs`）、新增产品（`products` 或某模块 `deep.tools`），还是补/改某模块的深度内容（`deep`）？
4. **按房规写**：遵守 `AGENTS.md` 第 9 节的结构与文风（见下方第 3 节速查）。
5. **逐条核实链接**：**每个 URL 必须实际访问确认可达（HTTP 200/正常重定向）**，记录跳转后的最终地址。**严禁凭记忆编造 URL。** 区分"读物"（放 `deep.links`）和"工具官网/文档"（放 `deep.tools[].links`）。
6. **盖更新日期**：把改动模块在 `moduleUpdated` 里的日期改成**当天**（`YYYY-MM-DD`）。
7. **跑链接体检**：`node tools/check-links.mjs`。确保新加链接可达；已存在的失效链接一并修掉或替换。
8. **本地验证**：
   - `node -c content.js` 和 `node -c app.js` 语法通过；
   - 本地起服务器（`python3 -m http.server`）打开页面，确认目标模块渲染正常、深链接可用、其它模块没被带坏。
9. **记账**：更新 `CHANGELOG.md`（新版本条目，说明改了什么）、把 `index.html` 页脚版本号与 `README.md` 的 "Current release" 同步升级。
10. **提交推送**：`git add` 相关文件 → `git commit` → `git push origin main`。推送后等 1–2 分钟，GitHub Pages 自动重新发布；用线上地址核对生效。

## 3. 写作格式速查（详见 AGENTS.md 第 9 节）

**深度模块 `deep` 的固定结构（顺序不可乱）：**
1. `intro` — 深入理解：为什么重要、和相邻模块的关系。一段话，先给直觉再展开。
2. `keyConcepts` — 关键概念展开：`[[概念名, 一段解释], ...]`。解释要具体、给场景。
3. `tools` — 上手工具/产品：每个 `{name, object, links:[[标签,URL]], learn}`。
   - `object`：**这个产品的"一等对象"是什么**（如 workflow、task、workspace、runtime、memory layer）。
   - `learn`：**怎么上手、用它学什么**。
   - `links`：官网 + 文档/教程，**已核实可达**。
4. `links` — 精选学习资料：`[[标题, URL, 一句推荐理由]]`，偏"读物"（文章/指南/视频），已核实可达。
5. `path` — 建议学习路径：`[步骤1, 步骤2, ...]`，从"先读什么"到"动手做什么"。

**文风：**
- 中文；简洁具体；先结论/例子，再展开。
- 避免长篇学术定义堆在例子前面；一屏不要塞太多新术语。
- 产品**必须回答**：一等对象是什么？怎么上手？（这个网站的核心价值是"把概念落到工具上"。）

## 4. 不可破坏的底线

- 保持**纯静态**：无构建步骤、无后端、无数据库、无框架依赖。
- 保持**模块化浏览**：总地图 → 单模块 → 深度章节。不要做成一篇长文瀑布。
- 保持深链接（`#模块id`）可用。
- 不把本仓库与 `personal-knowledge-management-solution` 合并（见 `docs/REPOSITORY_BOUNDARY.md`）。

## 5. 常见任务示例

**加一个新产品到某模块的工具区：**
1. 判断值不值得收（第 2 步）→ 2. 找到目标模块的 `deep.tools` 数组 →
3. 追加 `{name, object, links, learn}` → 4. curl/fetch 核实每个 link →
5. 刷新该模块 `moduleUpdated` 日期 → 6. 跑 `check-links.mjs` → 7. 本地验证 →
8. CHANGELOG + 版本号 → 9. push。

**加一个新概念释义：**
1. 在 `conceptDefs` 加 `'概念名':'一句话释义'` → 2. 若它归属某模块，确认该模块 `concepts` 数组也列了它 →
3. 本地验证概念索引显示正常 → 4. 记账 → 5. push。
